# Shell、文件权限、环境变量

## 一、Shell —— 你和操作系统之间的翻译官

### 1.1 是什么

**Shell**（壳）是运行在用户和内核（Kernel）之间的一个**命令解释器**。你在终端输入命令，Shell 负责解析它、调用对应的程序、把结果返回给你。

```
你  →  Shell  →  内核  →  硬件
        ↑
   解析命令 / 通配符 / 管道 / 变量
```

它之所以叫"壳"，是因为它包裹在操作系统内核外面，是你直接接触的那一层。

### 1.2 常见种类

| Shell  | 路径            | 说明                   |
| ------ | --------------- | ---------------------- |
| `sh`   | `/bin/sh`       | 最原始的 POSIX Shell   |
| `bash` | `/bin/bash`     | Linux 默认，功能最全   |
| `zsh`  | `/bin/zsh`      | macOS 默认，交互体验好 |
| `fish` | `/usr/bin/fish` | 语法友好，自带补全     |

查看当前用的是哪个：

```bash
echo $SHELL        # 登录时的默认 shell，如 /bin/bash
echo $0            # 当前正在运行的 shell
cat /etc/shells    # 系统里所有可用的 shell
```

### 1.3 Shell 的两种身份

- **交互式 Shell**：你敲一条，它执行一条。
- **脚本 Shell**：把命令写进 `.sh` 文件批量执行，这就是"Shell 脚本编程"。

```bash
#!/bin/bash
# 这是一个最简单的脚本
name="world"
echo "Hello, $name"
```

### 1.4 Shell 里最实用的能力

```bash
# 1. 管道：把上一个命令的输出，作为下一个命令的输入
ps aux | grep nginx        # 查看进程并过滤

# 2. 重定向
ls -l > out.txt            # 覆盖写入文件
ls -l >> out.txt           # 追加写入
command 2> err.txt         # 只重定向错误输出

# 3. 通配符
ls *.cpp                   # 匹配所有 .cpp 文件
rm file?.txt               # ? 匹配单个字符

# 4. 命令替换
echo "今天是 $(date)"
```

> 关键理解：**Shell 本身不是命令，它是命令的执行环境**。你敲的 `ls`、`grep` 都是独立程序，Shell 负责找到它们（靠 `PATH`，见第三节）并启动。

## 二、文件权限 —— Linux 的安全基石

### 2.1 一行 `ls -l` 拆解

```bash
$ ls -l
-rwxr-xr--  1 alice dev  4096 Oct 13 10:00 app.sh
↑└┬┘└┬┘└┬┘  ↑   ↑    ↑
│ │   │  └── 其他人(other)权限
│ │   └───── 所属组(group)权限
│ └───────── 属主(user)权限
└─────────── 文件类型
```

### 2.2 三组权限 + 三个对象

**权限（做什么）：**

| 符号 | 名称         | 对文件       | 对目录                |
| ---- | ------------ | ------------ | --------------------- |
| `r`  | read 读      | 读取内容     | `ls` 列出目录内文件   |
| `w`  | write 写     | 修改内容     | 在目录内创建/删除文件 |
| `x`  | execute 执行 | 作为程序运行 | `cd` 进入目录         |

**对象（对谁）：**

- **u** (user) 文件所有者
- **g** (group) 同组用户
- **o** (other) 其他人

> 目录的 `x` 权限很反直觉：**没有 `x`，即使有 `r` 也无法 `cd` 进去**。要访问目录里的文件，`x` 是必需的。

### 2.3 两种表示法

**符号法：**

```bash
chmod u+x app.sh          # 给属主加执行权限
chmod go-w secret.txt     # 去掉组和其他的写权限
chmod a+r readme.md       # 所有人可读(a = ugo)
```

**数字法（八进制）：** 把 `rwx` 看成二进制三位，`r=4, w=2, x=1`，相加：

```
rwx = 4+2+1 = 7
rw- = 4+2   = 6
r-x = 4+1   = 5
r-- = 4     = 4
--- = 0     = 0
```

```bash
chmod 755 app.sh    # rwxr-xr-x  属主全权，其他人可读可执行（常用）
chmod 644 file.txt  # rw-r--r--  属主可读写，其他人只读（普通文件默认）
chmod 600 key.pem   # rw-------  只有属主能读写（私钥必用）
chmod 777 dir/      # rwxrwxrwx  所有人全权（危险，别乱用）
```

### 2.4 改变归属

```bash
chown alice file.txt           # 改属主
chown alice:dev file.txt       # 改属主和属组
chgrp dev file.txt             # 只改组
chown -R alice:dev project/    # 递归修改整个目录
```

### 2.5 实战场景

```bash
# 让脚本可执行
chmod +x deploy.sh && ./deploy.sh

# SSH 私钥权限必须严格，否则 ssh 拒绝使用
chmod 600 ~/.ssh/id_rsa

# 共享目录：所有人可写，但文件默认只有自己可删
mkdir /shared && chmod 1777 /shared    # 1 是 sticky bit
```

> 补充：特殊的 **setuid / setgid / sticky** 位（对应数字前第 4 位），例如 `/usr/bin/passwd` 带 setuid，普通用户执行时临时获得 root 权限。`sticky` 位（`/tmp` 就有）保证目录里只有文件属主才能删除自己的文件。

## 三、环境变量 —— 进程的"上下文配置"

### 3.1 是什么

**环境变量**是操作系统保存的一组 **键值对**，会被**子进程继承**。程序通过读取它们来获取运行所需的配置，比如去哪找命令、用什么语言、连哪个数据库。

```bash
echo $HOME       # /home/alice
echo $PATH       # 命令搜索路径
echo $USER       # 当前用户名
```

### 3.2 查看与设置

```bash
env                 # 列出所有环境变量
printenv PATH       # 查看某个变量
echo $PATH          # 用 $ 取值

# 设置（当前 shell 会话有效）
export MY_VAR="hello"

# 只给单条命令临时用
LANG=C ls -l
```

### 3.3 进程继承关系（核心！）

```bash
# 父 shell 设置
export API_KEY="abc123"

# 在父 shell 里启动的子进程（如 python）能读到
python -c "import os; print(os.environ['API_KEY'])"   # 输出 abc123
```

```
父 Shell (export API_KEY)
   └── 子进程 python  ← 继承了 API_KEY
```

**注意区别：**

```bash
MY_VAR="local"     # 只是 shell 变量，子进程看不到
export MY_VAR     # 升级为环境变量，子进程可见
```

### 3.4 PATH —— 最重要的环境变量

当你不写完整路径直接敲 `gcc` 时，Shell 就是**从左到右遍历 `PATH` 里的目录**去找这个程序：

```bash
echo $PATH
# /usr/local/bin:/usr/bin:/bin:/usr/sbin

# 把新目录加进 PATH（注意用 : 拼接，别覆盖原值！）
export PATH="$PATH:/opt/myapp/bin"
```

> 常见错误：写成 `PATH=/opt/myapp/bin` 会**覆盖**掉原来的值，导致 `ls`、`cd` 都找不到。永远用 `$PATH:` 拼接。

### 3.5 持久化配置文件

`export` 只在当前会话生效，关掉终端就没了。要永久生效，写进启动文件：

| 文件                             | 生效范围             |
| -------------------------------- | -------------------- |
| `~/.bashrc`                      | 每个交互式 bash 会话 |
| `~/.bash_profile` / `~/.profile` | 登录时加载           |
| `/etc/profile`                   | 系统全局，所有用户   |
| `/etc/environment`               | 系统级环境变量       |

```bash
# 追加到 ~/.bashrc
echo 'export PATH="$PATH:/opt/myapp/bin"' >> ~/.bashrc
source ~/.bashrc     # 立即生效，无需重开终端
```

### 3.6 常用环境变量一览

| 变量               | 含义                         |
| ------------------ | ---------------------------- |
| `PATH`             | 命令搜索路径                 |
| `HOME`             | 用户主目录                   |
| `USER` / `LOGNAME` | 当前用户名                   |
| `SHELL`            | 默认 shell                   |
| `PWD`              | 当前工作目录                 |
| `LANG` / `LC_*`    | 语言与本地化设置             |
| `PS1`              | 命令行提示符样式             |
| `LD_LIBRARY_PATH`  | 动态库搜索路径（C/C++ 常用） |

## 四、三者如何串起来（一个完整例子）

假设你写了 C++ 程序并打包成脚本部署：

```bash
# 1) 环境变量：告诉程序去哪里找动态库
export LD_LIBRARY_PATH="/opt/myapp/lib:$LD_LIBRARY_PATH"

# 2) Shell：脚本根据环境变量决定行为
cat deploy.sh
#!/bin/bash
APP_HOME="${APP_HOME:-/opt/myapp}"     # 默认值语法
echo "Deploying to $APP_HOME"

# 3) 文件权限：让脚本可执行、让私钥安全
chmod 755 deploy.sh
chmod 600 config/secret.pem

# 4) 运行
./deploy.sh
```

- **环境变量** 提供配置和上下文；
- **Shell** 作为执行者解析命令、传递变量、启动进程；
- **文件权限** 保证只有合适的人能读/写/执行这些脚本和资源。

三者共同构成了 Linux 上"程序如何被找到、被运行、被保护"的完整链条。

# 进程、线程、信号

## 一、进程(Process)—— 程序的"运行实例"

### 1.1 是什么

**程序**是磁盘上的静态文件(如 `a.out`);**进程**是程序被加载进内存后**正在运行**的动态实例。同一个程序可以跑出多个进程,各自独立。

一个进程包含:

- **地址空间**:代码、数据、堆、栈
- **资源**:打开的文件描述符、信号处理表、环境变量
- **执行状态**:CPU 寄存器、PC(程序计数器)、栈指针
- **身份**:PID(进程号)、PPID(父进程号)、优先级

### 1.2 虚拟地址空间布局

```
高地址  ┌──────────────┐
        │   stack 栈    │ ← 局部变量、函数调用(向下增长)
        │      ↓        │
        │      ↑        │
        │   heap 堆     │ ← malloc/new(向上增长)
        ├──────────────┤
        │   bss         │ ← 未初始化全局/静态变量(初值 0)
        ├──────────────┤
        │   data        │ ← 已初始化全局/静态变量
        ├──────────────┤
        │   text 代码段  │ ← 只读,存放机器指令
低地址  └──────────────┘
```

> 每个进程都以为自己独占整块内存——这是**虚拟内存**制造的假象,由内核 + MMU 映射到真实物理页。

### 1.3 进程状态

```
             fork()
新建 ───────────► 就绪 ◄────────┐
                  │  ↑          │
       调度选中   │  │ 时间片用完 │ I/O 完成/信号
                  ▼  │          │
                运行 ──────► 阻塞
                  │      等待 I/O
          exit()  ▼
                终止
```

- **就绪(Ready)**:万事俱备,只差 CPU
- **运行(Running)**:正在占用 CPU
- **阻塞(Blocked)**:在等 I/O、锁、信号,给 CPU 也不要

### 1.4 三个关键系统调用

```c
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>

int main() {
    pid_t pid = fork();          // 复制当前进程
    if (pid == 0) {
        // 子进程分支:fork 返回 0
        printf("child  pid=%d\n", getpid());
        execlp("ls", "ls", "-l", NULL);   // 用新程序替换自身
    } else {
        // 父进程分支:fork 返回子进程 PID
        printf("parent pid=%d, child=%d\n", getpid(), pid);
        wait(NULL);              // 等待子进程结束,回收资源
    }
}
```

| 调用   | 作用                                                      |
| ------ | --------------------------------------------------------- |
| `fork` | 复制出一个几乎一模一样的子进程(写时复制 COW,不立即拷内存) |
| `exec` | 用新程序**替换**当前进程的代码/数据,不换 PID              |
| `wait` | 父进程等待子进程退出,回收僵尸进程,防止资源泄漏            |

> **僵尸进程(zombie)**:子进程已死,父进程没 `wait`,残留一条 PCB;父进程先死则子进程被 `init`(PID 1)收养。

```bash
ps aux        # 查看所有进程
ps -ef --forest   # 看进程树(父子关系)
top / htop    # 实时监控
```

## 二、线程(Thread)—— 进程内的"轻量执行流"

### 2.1 是什么

**线程**是进程内部的执行单元。一个进程可以有多个线程,**它们共享进程的地址空间和资源**,但各自有独立的执行路径。

| 维度     | 进程                    | 线程                     |
| -------- | ----------------------- | ------------------------ |
| 地址空间 | 独立                    | **共享**(同进程内)       |
| 创建开销 | 大(拷贝页表等)          | 小(只建栈和寄存器上下文) |
| 切换开销 | 大(需换地址空间)        | 小                       |
| 通信方式 | IPC(管道/共享内存/信号) | 直接读写共享变量         |
| 崩溃影响 | 互不影响                | **一个线程崩,整进程死**  |
| 身份     | PID                     | TID(线程号)              |

**线程独享**:栈、寄存器、程序计数器、TID、errno。
**线程共享**:代码段、数据段、堆、文件描述符、信号处理表、当前工作目录。

> Linux 内核里其实**没有独立的"线程"概念**——线程就是用 `clone()` 造出的、共享更多资源的"任务(task)"。所以进程和线程在调度器眼里是对等的。

### 2.2 为什么用线程

- **并发**处理多任务(如 Web 服务器每连接一线程)
- **共享数据方便**,不用像进程那样搞复杂的 IPC
- **创建/切换更轻**,适合高并发

### 2.3 POSIX 线程(pthread)示例

```c
#include <pthread.h>
#include <stdio.h>

void* worker(void* arg) {
    int id = *(int*)arg;
    printf("thread %d running\n", id);
    return NULL;
}

int main() {
    pthread_t t[3];
    int ids[3] = {1, 2, 3};
    for (int i = 0; i < 3; i++)
        pthread_create(&t[i], NULL, worker, &ids[i]);  // 创建线程
    for (int i = 0; i < 3; i++)
        pthread_join(t[i], NULL);                       // 等待回收
    return 0;
}
// 编译:g++ -pthread main.cpp
```

### 2.4 线程的代价:竞态与锁

多线程同时改共享变量会出乱子——这就是**竞态条件(race condition)**:

```c
int counter = 0;                 // 共享

void* add(void*) {
    for (int i = 0; i < 100000; i++) counter++;   // 非原子!结果 < 200000
    return NULL;
}
```

`counter++` 实际是"读→加→写"三步,可能被切换打断。解决靠**互斥锁**:

```c
pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;

void* add(void*) {
    for (int i = 0; i < 100000; i++) {
        pthread_mutex_lock(&mtx);     // 加锁,保证临界区互斥
        counter++;
        pthread_mutex_unlock(&mtx);   // 解锁
    }
    return NULL;
}
```

> 锁用多了会引入**死锁**:两个线程各持一把锁、又互相等对方的锁。原则:固定加锁顺序、尽量缩小临界区。

## 三、信号(Signal)—— 进程间的"异步通知"

### 3.1 是什么

**信号**是内核或进程发给某个进程的一个**软中断通知**,形式就是一个整数编号。它**异步**到达——进程不知道什么时候会来,来了就得处理。这是 Linux 最早、最原始的 IPC 机制。

```bash
kill -9 1234      # 向 PID 1234 发 SIGKILL
kill -l           # 列出所有信号
ctrl + C          # 终端给前台进程发 SIGINT
```

### 3.2 常见信号

| 编号 | 名称      | 默认行为       | 触发场景                        |
| ---- | --------- | -------------- | ------------------------------- |
| 2    | `SIGINT`  | 终止           | `Ctrl+C`                        |
| 9    | `SIGKILL` | 强制终止       | **不可被捕获/忽略**,终极杀招    |
| 15   | `SIGTERM` | 终止           | `kill` 默认信号,可被捕获做清理  |
| 11   | `SIGSEGV` | 终止+core dump | 段错误(非法内存访问)            |
| 6    | `SIGABRT` | 终止+core dump | `abort()`                       |
| 8    | `SIGFPE`  | 终止+core dump | 除零等算术错误                  |
| 13   | `SIGPIPE` | 终止           | 向已关闭的管道/套接字写         |
| 17   | `SIGCHLD` | 忽略           | 子进程退出/停止(父进程用来回收) |
| 18   | `SIGCONT` | 继续           | 恢复被暂停的进程                |
| 19   | `SIGSTOP` | 暂停           | **不可被捕获**,强制暂停         |
| 20   | `SIGTSTP` | 暂停           | `Ctrl+Z`                        |

> 关键对比:`SIGKILL(9)` 和 `SIGSTOP(19)` 是内核直接处理、**无法被程序改写**的;其余大都可以捕获或忽略。

### 3.3 信号的三种处置方式

1. **默认动作**:内核预定义(终止、忽略、core dump…)
2. **忽略**:`SIG_IGN`
3. **捕获**:注册一个处理函数(handler)

```c
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

void handler(int sig) {
    // handler 里只能调用"异步信号安全"的函数,printf 其实不严格安全
    write(1, "caught SIGINT!\n", 15);
}

int main() {
    signal(SIGINT, handler);          // 简化版注册(老接口)
    // 更规范:
    // struct sigaction sa = {0};
    // sa.sa_handler = handler;
    // sigaction(SIGINT, &sa, NULL);

    while (1) pause();                // 挂起等待信号
    return 0;
}
```

`Ctrl+C` 时它不会退出,而是打印 `caught SIGINT!`。

### 3.4 生命周期与两个重要概念

```
产生 ──► 递送(delivery) ──► 处理
  │
阻塞期间 ──► 未决(pending) 
```

- **未决(Pending)**:信号已产生但还没被处理,挂在进程的未决集合里
- **阻塞(Block)**:进程主动屏蔽某信号,期间它一直是未决状态、不递送(注意:阻塞 ≠ 忽略)
- **信号不排队**:同类标准信号若在未决期间又来一个,会被合并成一条

### 3.5 经典用法:用 SIGCHLD 回收子进程

```c
void reap(int sig) {
    while (waitpid(-1, NULL, WNOHANG) > 0);   // 循环回收所有已结束子进程
}
signal(SIGCHLD, reap);      // 子进程一退出就自动回收,避免僵尸
```

> 信号处理函数的铁律:**尽量短**,只做置标志位一类的操作,真正逻辑放到主循环里处理。此外 `sigaction` 比 `signal` 更可移植、语义更清晰,生产代码优先用它。

## 四、三者关系总览

```
┌─────────────────── 进程(资源分配的基本单位)───────────────────┐
│  地址空间 + 文件描述符 + 信号处理表                            │
│                                                                │
│   ┌─ 线程 A ─┐   ┌─ 线程 B ─┐   ┌─ 线程 C ─┐   ← 调度基本单位  │
│   │ 私有栈    │   │ 私有栈    │   │ 私有栈    │                 │
│   └──────────┘   └──────────┘   └──────────┘                 │
│        共享堆/数据/代码/文件                                   │
└────────────────────────────────────────────────────────────────┘
         ▲                              │
         │  信号(异步通知,可打断/终止进程或其线程)              
         └──────────────────────────────┘
```

- **进程** = 资源隔离的容器,是"分配内存和权限"的单位
- **线程** = 容器里的干活的执行流,是"内核调度 CPU"的单位
- **信号** = 外部(内核/其他进程)向这个容器投递的异步事件,能改变它的运行轨迹

一句话:**进程负责"拥有",线程负责"执行",信号负责"通知"**

# 虚拟内存、动态库

## 五、虚拟内存(Virtual Memory)

### 5.1 要解决什么问题

如果程序直接用物理地址,会有三个大麻烦:

1. **不安全**:进程 A 能随意读改进程 B 的内存
2. **不灵活**:程序必须整块连续加载,还得预先知道内存够不够
3. **难共享**:多个程序用同一份库,得各自复制

虚拟内存用一层"地址翻译"把物理内存抽象掉了。

### 5.2 核心思想:每个进程都以为自己独占内存

```
进程 A 眼里            物理内存            进程 B 眼里
0x0000...┌──────┐      ┌──────┐         ┌──────┐...0x0000
         │ 栈   │      │ 物理页│◄────────│ 栈   │
         │ 堆   │      │  4KB │         │ 堆   │
0xFFFF...└──────┘      └──────┘         └──────┘...0xFFFF
                 ↑
            MMU + 页表(Page Table)负责翻译
```

- CPU 发出的都是**虚拟地址**,不直接碰物理地址
- **MMU**(内存管理单元)查**页表**把虚拟地址翻译成物理地址
- 每个进程有**自己独立的页表**,所以看到的是互相隔离的地址空间

> 关键:**同样的虚拟地址,在不同进程里映射到不同物理页**。这就是隔离的来源。

### 5.3 分页与页表

内存不是按字节管理,而是切成固定大小的**页(page)**,常见 4KB。

```
虚拟地址 = [ 页号 (VPN) | 页内偏移 (offset) ]
                │              │
         查页表得到物理页号      原样保留
                │
物理地址 = [ 物理页号 (PFN) | 页内偏移 (offset) ]
```

页表项(PTE)里除了物理页号,还有关键标志位:

| 标志        | 含义                                    |
| ----------- | --------------------------------------- |
| **P**(存在) | 该页是否已在物理内存(否则触发缺页)      |
| **R/W**     | 可读/可写                               |
| **U/S**     | 用户态能否访问                          |
| **A/D**     | 是否被访问过 / 是否被写过(供置换算法用) |

多级页表是为了省空间:只给"用到的"那段地址分配页表项。

### 5.4 缺页中断(Page Fault)—— 按需加载的关键

```
CPU 访问虚拟地址 → MMU 查页表 → P=0(不在内存)
                                    │
                           触发缺页异常(陷入内核)
                                    │
                   内核把缺失的页从磁盘换入物理内存
                                    │
                        更新页表 → 重新执行那条指令
```

这就是**按需分页(demand paging)**:程序启动时并不真的把整个可执行文件读进内存,用到哪页才换哪页。

### 5.5 地址空间里的三种典型页

回到上节的进程地址空间,现在能看清每段的"身份":

- **text 代码段**:映射到可执行文件,只读、可共享
- **data/bss**:可读写,来自文件或清零
- **堆/栈/匿名映射**:没有文件对应(`mmap` 匿名页),按需分配
- **共享库**:多个进程的虚拟页映射到**同一份物理页**(这就是动态库省内存的原理,见第三节)

### 5.6 换页与置换

物理内存不够时,内核把不常用的页**换出(swap out)** 到磁盘,需要时再**换回**。常用置换算法:

- **LRU**(最近最少使用):淘汰最久没用的页,A/D 位就是给它用的
- **Clock / 二次机会**:LRU 的近似实现,开销更小

> **抖动(thrashing)**:内存严重不足,页面被疯狂换进换出,CPU 全耗在 I/O 上,系统几乎卡死。`vmstat`、`top` 里 `si/so`(swap in/out)飙高就是它。

### 5.7 直观感受一下

```bash
cat /proc/self/maps      # 看当前进程的虚拟内存映射(段 + 权限 + 来源文件)
```

输出里每行形如:

```
7f3a1c000000-7f3a1c021000 r-xp  /lib/x86_64-linux-gnu/libc.so.6
└── 虚拟地址范围 ──┘ └权限┘ └── 映射的文件(动态库!)
```

`r-xp` 表示只读+可执行+私有,`/lib/.../libc.so.6` 说明这段映射自 libc 动态库。**虚拟内存和动态库在这里合流了**。

### 5.8 顺便:用户态分配器

`malloc/new` 拿到的内存来自**堆**,底层靠两个系统调用向内核要页:

- **`brk/sbrk`**:抬高堆顶(小块、连续)
- **`mmap/munmap`**:映射匿名页(大块分配、glibc 对大对象走这条)

所以 `free` 后内存**不一定还给操作系统**,通常留在进程的内存池里下次复用——`valgrind`、`top` 里 RSS 不下降常被误当成泄漏,其实可能只是没归还。

## 六、动态库(Dynamic / Shared Library)

### 6.1 静态库 vs 动态库

| 维度       | 静态库 `.a`                | 动态库 `.so`               |
| ---------- | -------------------------- | -------------------------- |
| 链接时机   | 编译链接时**整体拷进**程序 | 运行时才加载、链接         |
| 可执行体积 | 大(每程序各留一份)         | 小                         |
| 内存占用   | 每个进程各一份             | **多进程共享同一份物理页** |
| 更新       | 改了库要**重新编译**程序   | 换 `.so` 即可,程序不用重编 |
| 部署       | 简单(自包含)               | 需保证目标机有对应 `.so`   |
| 启动速度   | 稍快                       | 需要加载+重定位,稍慢       |

> 核心价值:**代码复用 + 内存共享 + 独立升级**。系统里几乎所有程序都共享同一份 `libc.so.6`,不然内存早炸了。

### 6.2 编译与使用

```bash
# 生成动态库(-fPIC 生成位置无关代码,-shared 生成共享库)
g++ -fPIC -shared -o libmath.so math.cpp

# 链接:指定库路径 -L,指定库名 -l(注意:libmath.so → 写成 -lmath)
g++ main.cpp -L. -lmath -o app

# 运行:告诉加载器去哪找 .so
export LD_LIBRARY_PATH=.:$LD_LIBRARY_PATH
./app
```

| 参数           | 作用                                          |
| -------------- | --------------------------------------------- |
| `-fPIC`        | 生成**位置无关代码**,库可能被加载到任意地址   |
| `-shared`      | 产出共享库                                    |
| `-L.`          | 链接时在 `.` 目录找库                         |
| `-lmath`       | 链接 `libmath.so`(名字去掉 `lib` 前缀和`.so`) |
| `-Wl,-rpath,.` | 把搜索路径**写进程序**,免设 `LD_LIBRARY_PATH` |

### 6.3 为什么需要 PIC(位置无关代码)

动态库加载到哪个虚拟地址**编译时不确定**,所以代码里不能出现写死的绝对地址。

- 通过 **GOT(全局偏移表)** 间接跳转到外部符号
- 通过 **PLT(过程链接表)** 做函数的**延迟绑定(lazy binding)**:第一次调用某函数时才真正解析它的地址,之后走缓存

```
调用 printf:
  你的代码 → call printf@plt → 查 GOT 表 → 已解析? 直接跳
                                    │
                                 未解析 → 加载器搜索 libc → 填 GOT → 跳过去
```

> 这就是动态库"启动快、首次调用慢"的原因,也是 `LD_DEBUG=bindings ./app` 能看到绑定过程的原因。

### 6.4 加载流程(与虚拟内存的呼应)

```
1. 执行 ./app → 内核加载器读取 ELF 头
2. 看到 .dynamic 段 → 找到依赖的 libc.so、libmath.so…
3. 用 mmap 把这些 .so 的代码段/数据段映射进虚拟地址空间
4. 做重定位,填好 GOT/PLT
5. 跳到程序入口 _start → __libc_start_main → main
```

第 3 步的 `mmap` 正是虚拟内存的机制——**动态库本质就是被 `mmap` 进来的、可共享的虚拟内存段**。

### 6.5 查看与调试动态库

```bash
ldd app                    # 程序依赖哪些动态库(以及是否找到)
readelf -d app             # 看 ELF 的 .dynamic 段:NEEDED、RPATH 等
nm -D libmath.so           # 列出库导出的符号
objdump -T libmath.so      # 动态符号表
LD_DEBUG=libs ./app        # 打印库搜索过程(排查"找不到 .so"利器)
```

常见报错及原因:

```
error while loading shared libraries: libmath.so: cannot open shared object file
```

→ 加载器找不到库。解决顺序:

1. `export LD_LIBRARY_PATH=.:$LD_LIBRARY_PATH`
2. 编译时加 `-Wl,-rpath,/opt/myapp/lib` 固化路径
3. 拷进系统库目录 `/usr/local/lib` 并 `ldconfig`(改 `/etc/ld.so.conf` 后)

> 库搜索顺序大致是:`RPATH` → `LD_LIBRARY_PATH` → `/etc/ld.so.cache` → `/lib` `/usr/lib`。

### 6.6 版本管理:soname

生产环境动辄有 `libfoo.so.1.2.3`,靠 **soname** 做兼容:

```bash
g++ -fPIC -shared -Wl,-soname,libfoo.so.1 -o libfoo.so.1.2.3 foo.cpp
ln -s libfoo.so.1.2.3 libfoo.so.1     # 运行时按 soname 找
ln -s libfoo.so.1     libfoo.so       # 编译时按这个名字链接
```

- **大版本变** → 接口不兼容 → soname 变(如 `.so.1` → `.so.2`),新旧可共存
- **小版本变** → 向后兼容 → 共用同一个 soname

## 七、两者如何串起来

```
┌──────────────── 虚拟内存(给每个进程一套独立地址空间)────────────────┐
│                                                                        │
│   text(可共享)   data(私有)   heap   stack   ← 你的程序                  │
│       ▲                                                                │
│       │ mmap 映射,多进程共享同一物理页                                   │
│   ┌───┴────────────────────────────────────┐                          │
│   │  libc.so.6   libmath.so   …             │ ← 动态库                  │
│   └────────────────────────────────────────┘                          │
└────────────────────────────────────────────────────────────────────────┘
        ▲                                    ▲
        │ 缺页时按需从磁盘换入                  │ 加载器 mmap 进来 + 重定位
     页表/MMU                              GOT/PLT 延迟绑定
```

- **虚拟内存**提供隔离、按需加载、共享的底层机制
- **动态库**利用虚拟内存的映射与共享能力,实现代码复用与独立升级
- 二者共同回答了上节留下的问题:**程序"如何被加载"、内存"为何彼此隔离又能共享"**

一句话:**虚拟内存是"地址的抽象",动态库是"代码的复用",前者是机制,后者是策略**。
